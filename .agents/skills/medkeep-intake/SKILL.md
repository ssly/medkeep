# MedKeep - 成员调度与双轨数据录入 Skill (medkeep-intake)

本 Skill 是 MedKeep 系统的进门调度中心，死守四大核心机制：**成员交互防呆**、**医院正式单据与患者自查双轨隔离**、**自查分析手动打标确认** 以及 **存疑单据阻断与推断强制告知**。

---

## 核心机制一：双轨数据隔离架构 (Dual-Track Architecture)

为了保证医疗数据的严肃性与客观性，**严禁将患者主观病情分析或日常自测直接写入医院正式病历库**：

| 数据轨道 | 存储文件 | 数据性质 | 典型内容 |
| :--- | :--- | :--- | :--- |
| **轨道 A：医院正式客观单据** | `data/{person}-medical-records.jsonl` | 具备法律与医疗效力的官方单据 | 门诊病历、急诊记录、检验化验报告单、影像诊断单、处方笺、体检报告 |
| **轨道 B：患者病情观察与自查分析** | `data/{person}-observations.jsonl` | 患者自主观察、现象推测与日常自测记录 | 症状起病诱因推测、药物不良反应自查、冷热刺激反应、家庭血压/心率日记 |

## 核心机制二：自查分析手动打标确认协议 (Manual Promotion Protocol)

每当用户口述或记录一段病情观察、症状现象或自查推测时，Agent 必须执行以下流程：

1. **结构化提取**至 `data/{person}-observations.jsonl`：
   ```json
   {
     "obs_id": "OBS-DEMO-20260314-01",
     "person": "demo",
     "person_name": "张三（示例）",
     "date": "2026-03-14",
     "datetime": "2026-03-14 21:00",
     "topic": "resp",
     "title": "降温后夜间干咳与冷空气刺激观察",
     "phenomenon": "昨日气温骤降8度，晚间开窗通风后出现持续干咳，无发热无咳痰...",
     "self_analysis": "怀疑冷空气刺激诱发气道高反应性，拟前往三甲医院呼吸内科查血常规与听诊",
     "promoted_to_clinical_context": true,
     "linked_record_ids": ["DEMO-01", "DEMO-02"],
     "created_at": "2026-03-14T21:00:00Z"
   }
   ```

2. **强制主动向用户发起确认（必须征得用户同意方可打标）**：
   > 💡 **已为您保存该条病情自查分析**（编号：`OBS-DEMO-20260314-01`）
   > 
   > **请确认**：是否将该条记录标记为 **【正式临床引用】（Promote to Clinical Context）**？
   > - **若确认打标为【是】**（`promoted_to_clinical_context: true`）：后续生成门诊病史摘要、专科病情看板及医生问诊流会自动将其作为**关键患者自述病史**交叉引用；
   > - **若暂不打标【否】**（`promoted_to_clinical_context: false`）：仅保留在个人观察库中备忘，不干扰后续正式就诊时间线。

## 核心机制三：家庭成员识别与防呆

1. **核验既有成员**：
   - 读取 `config/medkeep.json`（若无则读取 `config/medkeep.template.json`）中的 `members` 列表。
   - 若用户输入已明确成员（如配置文件中已存在的成员姓名或拼音/英文 ID），直接提取其英文标识（`id`）。
2. **问询防呆**：
   - 若用户未指明人员且材料中名字模糊，**必须暂停并询问**：
     > “检测到您提交了新内容，请问该记录属于哪位家庭成员？（请参考 `config/medkeep.json` 中的成员列表；若是新成员，请输入英文ID与姓名，例如：`father` / `父亲`）”
3. **新成员自动建档**：
   - 向 `config/medkeep.json` 追加新成员；
   - 自动初始化 `data/{id}-medical-records.jsonl` 与 `data/{id}-observations.jsonl`。

## 核心机制四：存疑单据阻断与推断强制告知 (Clarity & Inference Guard)

医疗数据零容错。在解析单据并写入 `data/{person}-medical-records.jsonl` 时，必须严格执行以下三级校验：

1. **不可推断的模糊/残缺项（强制阻断确认）**：
   - 若单据因拍摄反光、失焦、裁切或极度潦草的手写体，导致**就诊日期、核心诊断、药物名称/用法剂量、关键异常指标数值**无法 100% 确定，**严禁猜测编造**！
   - 必须向用户发起阻断确认：
     > ⚠️ **检测到以下单据存在无法确认的模糊/缺失信息，已暂停对应字段定稿**：
     > - **文件名**：`xxx.jpg`
     > - **存疑位置**：（例如：处方第 2 项手写药名模糊 / 检验单右侧参考值裁切）
     > - **请您确认**：请重新上传清晰照片，或直接回复补充该处内容。

2. **可推断的手写批注与单据内笔误（强制写入 `agent_inference` + 默认 `manual_confirmed: false`）**：
   - 若单据上存在**医生手写批注**（如手写退热药使用频次、药膏涂抹天数、临时增减药量）或**门诊医生手打录入与化验单原件的微小笔误差异**，即使 Agent 能结合医学常识或同日检验单推断出准确含义，也**绝不能静默处理**。
   - **入库 JSONL 强制字段要求**：
     - `"agent_inference"`: 必须以 `"AGENT：推断意见——..."` 开头，完整说明原件手写/差异情况及 Agent 的推断依据；
     - `"manual_confirmed"`: **默认必须设为 `false`**（用户可在对话中向 Agent 确认修改，也可直接在 Web 看板页面上点击「✓ 确认无误」或「编辑备注」更新为 `true`）。
   - **必须在完成归档后的回复中专门列出「手写辨识与推断核对清单」**，展示“原图字迹 ➡️ Agent 推断结论”，请用户做最终人工复核。

3. **诊疗链路缺页/关联报告缺失标记（写入 `missing_items`）**：
   - 当门诊病历中明确记载开具了某项重要检查/检验（如常规检查、影像、专项化验）但未见对应独立报告原件时，在该条记录中写入 `"missing_items"` 数组：
     ```json
     "missing_items": [
       {
         "category": "imaging",
         "type_label": "影像缺失",
         "title": "胸部X光正侧位片诊断报告单",
         "reason": "病历内已载明开具检查或结论引述，但缺少独立影像报告单原件。"
       }
     ]
     ```
   - 若某日仅有化验/检查单而无门诊病历底纸，`server.py` 会自动生成 `病历缺失` 标记。

4. **重复与补拍单据比对联动（调用 `medkeep-archive` 优选流水线）**：
   - 当检测到新摄取的单据已存在同日同类既有原件时，联动 `medkeep-archive` 执行四级质量对比（P0完整性 > P1清晰度 > P2反光 > P3平整度）；
   - 若新图胜出，经 2400px 统一压缩置换落盘后，同步更新对应 JSONL 记录（修正或清除旧图中的模糊推断标记与缺失项）；
   - 若既有图更优，保留原件并对用户说明原因；若存在页面互补则增量补全。

## 核心机制五：服务启动受控原则 (No Auto-Launch on Data Processing)

资料摄取与入库处理过程中，**绝对严禁擅自在后台执行 `python3 server.py` 启动或重启服务**，除非用户在指令中有明确说明。
归档完成后，仅需在回复末尾告知用户启动命令与访问入口：
> 💡 **启动看板与访问方式**：  
> 终端运行：`python3 server.py`  
> 访问地址：`http://127.0.0.1:8765`
